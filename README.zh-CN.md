# Feature & Bug Fix Skill：新增功能与 BUG 修复

[English](README.md) | [简体中文](README.zh-CN.md)

这套技能让 AI 按照固定流程处理新增功能和 BUG 修复：
**先调查 → 出方案 → 用户确认 → 按方案修改 → 验证结果**。

技能指令用英文写，方案、问题、进度和结果默认使用大白话中文。
不预设具体业务，任务细节从实际需求、仓库和项目规则中获取。

## 它会做什么

- 先读懂受影响的流程，检查相关调用方，再提出修改建议。
- 区分已确认事实、代码推断和未验证假设。
- 查找根本原因，优先复用已有能力。
- 明确要改的文件和函数，说明各模块分工。
- 按实际影响检查异常、并发、兼容性和资源开销。
- 提前约定能观察到结果的验收方法和旧功能回归检查。
- 等用户确认当前方案后才修改文件。
- 如实说明改了什么、验证了什么、还有什么没有验证。

## 安装到 Codex

使用默认 Codex 目录时，执行以下命令，安装到当前用户的全局技能目录：

```sh
mkdir -p "$HOME/.codex/skills"
git clone https://github.com/ccecai/feature-bugfix-skill.git "$HOME/.codex/skills/feature-bugfix"
```

如果设置了自己的 `CODEX_HOME`，改为放到它下面的 `skills/feature-bugfix`。
客户端尚未发现技能时，开启新会话或重启客户端后使用。

## 安装到 Cursor

执行以下命令，安装到本机当前用户的全局技能目录，各项目都可以使用：

```sh
mkdir -p "$HOME/.cursor/skills"
git clone https://github.com/ccecai/feature-bugfix-skill.git "$HOME/.cursor/skills/feature-bugfix"
```

需要时重新打开 Cursor。只想在某个项目使用时，把技能放到该项目的
`.cursor/skills/feature-bugfix/` 或 `.agents/skills/feature-bugfix/`。
包含 `SKILL.md` 的文件夹应命名为 `feature-bugfix`。

这些命令需要 Git，以及 macOS 终端或 Linux 等 POSIX shell。
私有仓库需要使用有访问权限的 GitHub 账号认证。
如果目标目录已经存在，先查看并备份，再决定如何替换；克隆命令不会覆盖已有安装。

技能发现和不同环境的区别，参见 [Cursor 官方说明](https://cursor.com/docs/skills)。
本地安装不会自动将技能部署到远程环境或 ChatGPT 账号。

## 怎么使用

客户端发现技能后，用户提出新增功能、增强功能或修复 BUG 的请求时，
助手可以根据请求内容自动选择它，例如：

- `新增功能` / `新增需求`
- `修复 bug` / `修复 BUG`
- `add a feature` / `fix a bug`

这里按请求意图匹配，并不是输入关键词就执行的程序钩子。
只是引用这些词、解释问题、单纯审查代码，或者创建和修改提示词、技能本身时，不触发。

可以直接描述任务，也可以参考下面的格式。已有信息不必重复填写：

```text
类型：新增功能 / 修复 BUG
现象或需求：……
期望结果：……
已知条件：……
必须保持的行为：……
本次不做：……
```

在 Codex 中也可以明确调用：

```text
$feature-bugfix 先调查这次需求或 BUG，用中文提出最小改动方案。
```

在 Cursor 中输入 `/`，从命令菜单选择 `feature-bugfix`。

## 什么时候开始改代码

用户批准前，只做只读调查。
不创建、修改或删除文件，不切换分支，不提交，不执行 stash、reset 或 rebase。
会写入产物的构建和测试，也等批准后再运行。

方案按六项说明：

1. 目标和根本原因。
2. 现有流程和可复用能力。
3. 最小改动和职责分工。
4. 风险、异常和资源开销。
5. 验收和验证。
6. 反向检查方案，以及需要用户决定的事项。

看完当前方案后，回复：

```text
按方案做
```

明确要求实施当前方案的其他说法也算批准。
最初提出“修复 BUG”不等于批准还没有展示的方案；没有回复也不等于同意。

实施时只做批准范围内的修改。
确实需要扩大范围，或者发现遗漏的安全、并发、兼容性问题时，先提出修订方案。
同一方案已经批准，不重复要求确认。

## 怎么验证和汇报

检查要覆盖实际行为和结果。
仅仅编译通过、函数存在或退出码为零，不能证明功能正确。
不能靠删除测试、跳过失败项、放宽断言、屏蔽错误或绕过真实逻辑让检查通过。

最后用中文逐项说明：

1. 外部能观察到的行为改了什么。
2. 实际改动是否符合批准的方案。
3. 运行了哪些检查，结果是什么。
4. 哪些没有验证，仍有什么风险。
5. 是否达到约定的验收标准。

“代码已修改”“构建通过”“测试通过”“实际运行验证通过”要分开说。
缺少证据的地方必须保留说明。

## 使用边界

- 技能提供工作指令，不额外提供工具、仓库访问或权限。
- 继续遵守实际适用的 `AGENTS.md`、项目规则和用户当前的明确指令。
- 保留用户已有改动和其他正在进行的工作。
- 批准代码方案，不等于批准提交、推送、发布、破坏性操作或扩大访问权限。
- 减少改动不能牺牲正确性、安全、错误处理和响应要求。
